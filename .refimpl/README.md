# 参考实现（先别看）

这个目录里是 `code/` 那 39 个 `TODO` 的**完整实现**，一个 `.cc` 对一份。
它不参与 `code/` 的构建——`CMakeLists.txt` 里根本没有它，所以你 `cd code`
编译的时候，它连被扫到都做不到。

把它跑起来（在**仓库根目录**执行）：

```bash
bash .tools/fast.sh          # 把参考实现叠到一份临时副本上，编完跑全量，跑完就没了
bash .tools/verify.sh        # 同上，但会保留日志，用于确认「测试本身是对的」
```

两个脚本都只改 `/tmp` 下的副本，**不会动你 `code/` 里的任何一行**。

## 为什么要藏

不是防抄袭。是「知道答案就在旁边」这件事本身会改变你写代码的方式：
本来你会盯着报错想十分钟，一旦答案唾手可得，那十分钟就没了，而那十分钟
才是这门课真正教东西的地方。

## 什么时候可以打开

- 同一个 `TODO` 卡了两小时以上，且已经按「检查点 → 诊断表 → sanitizer → 最小复现」走过一遍
- 阶段做完了，想对照一下自己的写法和别人的差别（这一步比你想的有用：同样的功能，几十行和几百行的区别往往就是「有没有处理那个边界」）
- 想验证「我的测试到底测没测到东西」——把参考实现里某个边界改坏，看测试红不红

## 它不是标准答案

它是**一个**能通过全部 102 个用例的写法，不是唯一写法，也不保证是最优写法。
比如 L0 挑选 compaction 输入时它直接全拿（简单、符合不变量），而 LevelDB 会
先扩一圈再比总量。你觉得你的写法更好，那就用你的。
